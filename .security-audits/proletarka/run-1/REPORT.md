Дата: **18 ноября 2026**, Europe/Moscow. Исследовано рабочее дерево на базе `046a695ea632c601b10e4a547f52f868e07b4d7c`. Полная карта — [architecture.md](architecture.md), структурированные прикладные findings — [findings.json](findings.json), технические цепочки — [FINDINGS-DETAIL.md](FINDINGS-DETAIL.md).

## Общая оценка

**В приложении есть реальные пробелы контроля доступа; обновление Next.js и единая серверная авторизация требуют приоритета.** Подтверждены два прикладных дефекта: публичная выдача метаданных черновиков и отсутствие отзыва уже выданной сессии. Кроме того, lockfile содержит Next.js с актуальными HIGH/CRITICAL advisories; для DoS совпадают версия и используемая функциональность. Отказ сервиса не воспроизводился. **Удалённое выполнение кода, захват VPS, доступ к БД/бакету «Гикотеки» и анонимное изменение архива не подтверждены.** Это не означает, что таких путей нет: критические runtime- и инфраструктурные условия пока неизвестны.

Аудит относится к предоставленному репозиторию, а не к фактически запущенному образу. Стек в lockfile достаточно современный; проблемы нельзя объяснять одним возрастом кода. Контроль доступа опирается преимущественно на proxy, хотя административные API и операции требуют собственной проверки.

## SEC-01 — административный поиск раскрывает черновики

**Проблема и путь.** Matcher `src/proxy.ts:35–36` защищает `/admin/:path*`, но не `/api/admin/*`. Все четыре поисковых обработчика не требуют сессии: `people/search/route.ts:6`, `materials/search/route.ts:14`, `group-photos/search/route.ts:6`, `sources/search/route.ts:4` (относительно `src/app/api/admin/`). В materials условия `:33–41`, `:69–75` не содержат `status=published`. Group photos выбирает `id/title/status` на `:25–39`, имена связей на `:45–54`, возвращает их на `:76–87`.

**Условия.** Есть подходящий по поисковой строке черновик; запрос доходит до Next.js без отдельной авторизации NGINX. Имена людей и названия источников могут и так быть публичными — сам факт доступности этих двух API не назван самостоятельной утечкой. Граница черновика подтверждается публичной страницей `src/app/materials/[id]/page.tsx:24–27`, отвергающей неопубликованный материал.

**Последствия.** Посетитель без cookie узнаёт названия, ID, типы и связи неопубликованного контента; group photos выдаёт статус. Тело материала, пароль, содержимое файла и S3 credentials этим API не раскрываются.

**Безопасное воспроизведение.** Только в локальной изолированной копии создать тестовое групповое фото `Audit Draft` со статусом draft; выполнить `GET /api/admin/group-photos/search?q=Audit` без cookie. Ожидается выдача записи вместо 401. Для materials аналогичный GET. В ходе аудита реальная БД не использовалась: harness исполнил исходный GET с fixture DB и подтвердил отсутствие auth до обращения к ней и сериализацию draft metadata. Это не HTTP end-to-end проверка production.

**Минимальное исправление.** Общий `requireAdmin` с проверкой валидной сессии, существующего пользователя и роли в начале каждого admin API, до запросов БД. Ограничение matcher можно добавить вторым слоем. Не заменять guard одним published-фильтром: редактору нужен поиск черновиков, а сам endpoint административный.

**Проверка исправления.** Для всех четырёх API: без сессии/с истёкшей/отозванной — 401/403 и ноль запросов к БД; с администратором — прежний результат, включая draft в редакторском поиске. Публичный поиск, если требуется, должен иметь отдельный контракт.

## SEC-02 — смена пароля и выход не отзывают скопированную сессию

**Проблема и путь.** `createSession` выдаёт JWT на 7 суток (`src/lib/session.ts:5`, `:18–22`). `getSession` проверяет подпись/exp (`:34–43`), proxy делает то же (`src/proxy.ts:19–24`). `deleteSession` удаляет cookie только в текущем клиенте (`session.ts:47–49`). `updatePassword` меняет только bcrypt hash (`src/app/admin/settings/actions.ts:43–47`). Нет таблицы сессий, tokenVersion или связи JWT с текущим паролем.

**Условия.** Атакующий уже получил копию действующего токена: самостоятельный путь кражи не установлен. Секрет подписи после этого не ротировался. Остаточная действительность составляет до 7 суток **от выпуска**, не новые 7 суток после выхода/смены пароля.

**Последствия.** Выход и восстановление контроля через смену пароля не прекращают доступ держателя старой сессии. Существующий пользователь проходит currentUser, старый JWT проходит proxy. Удаление пользователя не проверяется большинством read paths, но удаление пользователей через UI в рамках аудита не установлено.

**Безопасное воспроизведение.** Изолированный harness с одноразовым ключом: выпустить JWT для фиктивного пользователя, сохранить копию, вызвать deleteSession, проверить отсутствие cookie; подставить сохранённую копию в fixture cookie store — getSession снова возвращает пользователя. Реальные cookie/пароли не использовались. Для смены пароля доказательство статическое: меняется только hash. Будущая staging-проверка — два клиента одной fixture-учётки, сменить пароль в первом и выполнить безопасный read во втором.

**Минимальное исправление.** Выбрать серверные session ID с отзывом конкретной сессии либо sessionVersion, проверяемую на защищённых операциях и инкрементируемую при смене пароля/полном отзыве. Если требуется отзыв только текущей сессии при logout, нужен per-session identifier/store, одной глобальной версии недостаточно. Ротация SESSION_SECRET годится для аварийного выхода всех, но не заменяет штатное управление сессиями.

**Проверка исправления.** Старая сессия отвергается после отзыва/смены пароля; новая работает; срок и подпись проверяются; отсутствие/удаление пользователя закрывает доступ. Явно определить, выходит ли logout из одной сессии или из всех.

## Гипотезы, требующие runtime или инфраструктурной проверки

### H-01 — административные actions без серверного guard

`src/app/admin/actions.ts:67`, `people/actions.ts:75`, `artifacts/actions.ts:27`, `entities/actions.ts:20`, `topics/actions.ts:63` выполняют редакторские изменения без requireAdmin. `src/lib/logAdminAction.ts:14–15` просто прекращает журналирование при отсутствии сессии; он не запрещает уже выполненную операцию. В отличие от них `settings/actions.ts:11–16` и `comments/actions.ts:11–14` проверяют сессию.

Обычный запрос `/admin/*` защищает proxy. В установленном Next action dispatch зависит от manifest, ID, worker forwarding и текущей страницы (`node_modules/next/dist/server/app-render/action-handler.js:451`, `:723`, `manifests-singleton.js:201`). Нельзя считать отсутствие guard само по себе доказательством анонимной записи. Случайный ID не является auth-гарантией: [первичный advisory об action references](https://github.com/vercel/next.js/security/advisories/GHSA-955p-x3mx-jcvp) отмечает их возможную доступность в client artifacts.

Если цепочка подтвердится, последствия включают создание/изменение/удаление архива, публикацию и операции с объектами фиксированного S3 bucket. Это CRITICAL по критериям задания, **не доказанное выполнение кода на VPS**. Минимальная защита уже ясна: guard первым действием каждой экспортируемой admin mutation, независимо от proxy и страницы.

Безопасная последующая проверка: actual production build в изолированной копии с fixture DB/S3, проверка отказа неавторизованных вызовов до любого побочного эффекта, включая transport variants. Нужны build manifest и конфигурация worker/NGINX; на production не выполнять изменяющие запросы.

### H-02 — proxy bypass при чтении страниц

В admin layout children выводятся даже без session (`src/app/admin/layout.tsx:12–26`); например `src/app/admin/materials/page.tsx:38–90` сам запрашивает черновики без проверки пользователя. Известный framework advisory и matcher делают риск существенным. Нужна проверка реальной сборки/transport routing: обычный URL не доказывает защиту всех вариантов. Минимум — актуальный Next + auth рядом с DAL/страницами и API; один layout guard не заменяет guards действий.

### H-03 — обработчик оптимизации изображений и RCE

Отсутствие `next/image` в компонентах **не означает**, что `/_next/image` отключён: `next.config.ts:3–5` содержит только standalone. При неизвестной доступности источников/redirect handling нельзя исключить использование image optimizer. Но уязвимый package range без контролируемого decoder input и подходящей платформы не доказывает RCE. Сам `src/lib/s3.ts` ничего не декодирует/исполняет. Нужны actual image libc/native dependencies, разрешённые image источники, reachability и обратный proxy. Использовать только безопасные изображения в staging; payloads для memory corruption не запускать.

### H-04 — комментарии: quota, IP и повторное решение ALTCHA

`src/app/comments/actions.ts:36–43` принимает первый элемент X-Forwarded-For, затем X-Real-IP. При отсутствии IP quota пропускается (`:125`); count и insert разделены (`:125–148`). ALTCHA имеет expiry 5 минут, но не одноразовый consume (`src/app/comments/altcha.ts:15–25`). Если NGINX сохраняет клиентский XFF как первый элемент, квоту можно обойти; несколько параллельных разрешённых запросов могут пройти check до insert. Это даёт pending spam, расход БД и webhook notifications, **не автоматическую публикацию комментариев**.

Неизвестны sanitation/real_ip/rate limiting NGINX; поэтому обход на production не подтверждён. Повтор ALTCHA сам по себе не обходит корректную IP quota. Минимум: доверять только заголовку, перезаписанному доверенным proxy, ограничивать anonymous endpoint внешне и атомарно учитывать quota. Для сильной защиты — consume challenge один раз. Проверка только на fixture DB и известной proxy-конфигурации, без flood.

### H-05 — credentials, сеть и соседний проект

Приложение и мигратор используют `DATABASE_URL` (`docker-compose.yml:11`, `:36`); мигратор требует DDL (`README.md:20`). Неизвестно, использует ли production superuser, общую роль, межбазовые grants или широкие S3 credentials. `docker-compose.yml:5`, `:56–58` задают внешнюю backend network; `:8–9` — доступный host gateway. Это пути потенциального бокового движения после первоначальной компрометации, не подтверждённый выход из контейнера.

Нужны SELECT из каталогов PG о текущей роли/членстве/CONNECT/правах, inspect фактических сетей/монтирований и IAM/policies Hostkey. Отдельные имена БД и бакетов не гарантируют разграничение прав. Адреса/достижимость соседних сервисов в ходе аудита не сканировались.

## LOW / рекомендации по усилению защиты

Эти пункты не входят в подтверждённые findings без самостоятельной атаки:

- **Secure cookie:** `src/lib/session.ts:28` и `docker-compose.yml:26` включают Secure только явно; default false. README требует true. Проверить actual значение, HTTPS redirect/HSTS. При корректном HTTPS с HSTS HTTP-кража cookie не доказана.
- **Перебор входа:** оба login actions (`src/app/login/actions.ts:10–20`, `src/app/admin/login/actions.ts:10–20`) не ограничивают попытки. Защита может быть в NGINX; проверить оба пути, лимит по аккаунту и источнику, избегать постоянной блокировки чужого аккаунта. Не тестировался массовый перебор.
- **CSRF:** Server Actions имеют встроенную Origin/Host проверку в установленном Next; SameSite=Lax уменьшает межсайтовую передачу cookie. Отсутствие отдельного CSRF token не названо уязвимостью. Logout POST не имеет собственного Origin guard, но межсайтовая эксплуатация/существенный ущерб не доказаны. Проверить доверие X-Forwarded-Host/Host на NGINX.
- **Upload:** `src/lib/s3.ts:30–31`, `:51–55` доверяет MIME клиента, не magic bytes; 10MiB проверяется после чтения в память. Учитывать framework/default body limit, NGINX client_max_body_size и max dimensions при появлении decoder. UUID key, фиксированный bucket, отсутствие исполнения защищают от простой filename RCE. Улучшение MIME/extension validation желательно, но доверенный admin по дизайну не отдельный атакующий.
- **Публичные файлы:** `.env.example` явно требует публичное чтение uploads. Черновик материала не делает его S3-файл приватным; приватность файла по одному статусу не обещать. Если она нужна, потребуется отдельное правило доступа, а не только сложный ключ. Anonymous write/list bucket и доступ соседнего проекта не установлены.
- **Секреты:** `.env` не tracked, Docker context исключает `.env*`, JWT/ключи S3 не выводятся в JSX. Проверка значений/энтропии, backup history, внешних logs/CI artifacts не выполнялась. Дать runtime роли только свой bucket/prefix и минимальные DB grants; миграции отделить по роли.
- **Контейнер:** runtime UID 1001, socket/privileged/host volumes в service app не заданы. Планово: drop capabilities, no-new-privileges, ресурсы/PID limits, по возможности read-only rootfs с явно выделенными tmp/cache. Проверять на совместимость Next. Плавающие tags требуют контроля digest/rebuild cadence, не являются самостоятельной CVE.
- **Валидация CRUD:** типовые assertions не runtime validation. Добавить bounded validation строк/чисел/enums на server actions вместе с guards. Полностью доверенному admin разрешено редактировать весь архив; это не mass-assignment escalation между несуществующими ролями.
- **Гонки/целостность:** часть admin edits заменяет связи последовательными delete/insert без общей transaction, в частности `src/lib/adminSources.ts:29–42`, `:44–57`. При сбое/конкурентном редактировании возможна потеря связей; самостоятельного повышения полномочий не установлено. Импорт создания человека использует transaction. Сначала защищать границы, затем атомарность рискованных составных edits.

## Риск для соседнего проекта «Гикотека»

SEC-01 ограничен метаданными «Пролетарки». SEC-02 даёт редакторские полномочия при наличии украденной сессии, но не shell/доступ к env. Даже потенциальный H-01 предоставляет операции приложения, а не автоматически доступ к PostgreSQL superuser или Docker.

Наиболее опасная условная цепочка: RCE в процессе Next/native decoder → чтение доступных процессу DATABASE_URL/S3/webhook secrets → соединения через общую backend network/host gateway → чужие данные, **если** роли, S3 policy или соседние сервисы разрешают это. Наличие общей сети не обходит пароли/ACL. Непривилегированный UID ограничивает ущерб, но не защищает секреты самого процесса. Подтверждения container escape или доступа к данным «Гикотеки» нет.

DoS процесса «Пролетарки» может повлиять на соседей через общие CPU/RAM, если отсутствуют реальные cgroup limits; в предоставленном Compose лимиты не заданы. Это условный инфраструктурный blast radius, не измеренный отказ «Гикотеки».

Минимальная изоляция: отдельные роли без superuser/createrole/членства в серверных file/program roles, grants только своей БД/схеме; отдельные bucket-scoped ключи; отсутствие ненужной связности между проектами; запрет Docker socket/host mounts; limits и актуальный runtime. CONNECT к чужой БД — только возможность подключения, не доказательство чтения её таблиц.
